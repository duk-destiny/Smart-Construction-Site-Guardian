# 工单闭环与对标改进方案（评审稿）

> 背景：第 1 期优秀作品分享《智安协同助手》展示了「上报 → 提取 → 制度检索 → 派发到人 → 进度跟进 → 验收销项 → 周报复盘」的完整业务闭环。
> 本文档对照该案例，逐条列出现有系统（智护工地）的结构性缺口与对应解决方案，按优先级排列，供评审后实施。
>
> **差异化标准答案**（"你们和对标作品区别在哪？"）：对方优势是完整业务工单闭环，
> 感知依赖通用大模型；我们优势是自研视觉检测、本地 RAG、纠偏复训数据闭环——
> 本次迭代补齐工单全业务流程、保留既有强项，不照搬云端多模态路线：
> **本地离线优先、云端仅可选增强、关键业务节点保留人工确认、定级与派发靠确定性规则。**

---

## 一、现状定位：两边的长短板

| 维度 | 《智安协同助手》 | 智护工地（现状） |
| --- | --- | --- |
| 隐患感知 | 依赖通用多模态大模型读图，无自研检测指标 | ✅ YOLO 双场景自研权重，独立测试集逐类 P/R/F1 |
| 规范检索 | 有知识库 | ✅ BGE+Chroma 本地 RAG，条款可引用、防编造 |
| **自然语言上报（文字/语音）** | ✅ 云端多模态模型提取 | ⚠️ 仅作业票结构化字段；自由文本/语音上报路径缺失 |
| 研判深度 | LLM 单趟生成 | ✅ 多 Agent 编排、误报过滤、复核标记、证据链落库 |
| **工单派发到人** | ✅ 按责任分区匹配分包商负责人 | ❌ 生成的工单无接收人概念 |
| **进度跟进/催办** | ✅ 自动跟节点、超时追问 | ❌ 无状态流转，唯一 UPDATE 是文案回填 |
| **验收销项** | ✅ 负责人提交、安全员终审 | ❌ 无验收环节 |
| **风险周报** | ✅ 按等级汇总辅助复盘 | ⚠️ 有历史页/导出，无定期汇总推送 |
| 语音输入 | ✅ 文字/语音/图片 | ⚠️ 文字/图片，缺语音 |
| **人工纠偏→模型复训数据闭环** | ❌ 无 | ✅ 改判/纠偏→审核→confirmed 回写训练集→复训切换（独有） |
| 部署形态 | 云端工作流平台 | ✅ 全离线单机，断网降级齐全 |

结论：感知、研判、数据闭环是我们的强项；**业务闭环（派发→跟进→销项→复盘）是明显缺口**，
也是案例的核心叙事点，必须补齐。

## 架构总览：双通路输入（答辩口径，编号外插章）

> 系统提供两类并行输入通路：
> **① 多模态感知通路**——接收 RTSP 视频流、现场照片与结构化作业票字段，
> 经 YOLO 检测、规范 RAG 校验自动识别安全隐患（系统观察现实）；
> **② 任务指令通路**——接收用户文本指令（后续含语音转写），经封闭集意图识别
> 调度系统服务，完成建单/查询/统计/周报等业务操作（用户主动操控系统）。
> 两路共享同一会话上下文（`current_task_id` 指针 + DB 持久化）、同一工具组件
> （severity 映射/派发规则/TaskService/审计），实现隐患感知与业务操控一体化。

事实边界（防评委追问）：①中作业票为**结构化字段解析，无 OCR**（扫描件识别列
二期路线图）；实时高危告警当前仅落 `alarm_events`，产工单由 P0「告警→工单桥」
接通；指令通路为**封闭意图集 + 确定性执行端**，非开放式 function-calling。

## 二、P0：工单闭环补全（必做）

设计原则沿用既有哲学：**定级与派发靠确定性规则；智能只做非判定性辅助**（Q3/Q6 一致）。

### 2.1 数据模型（`dao/schema.sql` + `_MIGRATIONS` 增量迁移）

```sql
-- work_orders 追加列
assignee_id    TEXT REFERENCES users(id),   -- 整改责任人（可空=待指派）
status         TEXT NOT NULL DEFAULT 'open',-- open / submitted / closed / rejected
deadline       TEXT,                        -- 按风险等级默认：重大立即/较大2h/一般24h
submitted_note TEXT,                        -- 整改说明（责任人填写）
submitted_imgs TEXT,                        -- 整改现场照片路径(JSON 数组)
approved_by    TEXT, approved_at TEXT,      -- 验收人与时间
closed_at      TEXT,
```

- 「逾期」为派生状态（now > deadline 且未 closed），**不入库**，避免状态机膨胀；
- `status=rejected`（验收驳回）回到 `open` 并追加驳回原因，同单可多轮整改，全程留痕。

### 2.2 角色与账号（`services/auth_service.py` / `core/bootstrap.py`）

- `_ROLE_ACTIONS` 新增 `"responsible": {"view", "rectify"}`；
- `bootstrap.py` 种子演示账号：分包商责任人 `lisi / demo1234`（responsible）；
- 权限校验复用 `PermissionService`，责任人不进管理端，只能看到派给自己的单子。

### 2.3 派发规则（数据驱动，`config/config.yaml`）

```yaml
dispatch:
  rules:                       # 自上而下按序首中即用
    - scene: hot_work          # 场景匹配
      zone: 动火区A            # 可选：作业票 zone 字段细分
      assignee: lisi
    - scene: construction_ppe
      assignee: wangwu
```

- 匹配键：作业票区域字段 > 场景 > 兜底待指派池（admin 页面手动分派）；
- 安全员在报告页一键确认或改派 AI 的建议目标（人工有最终裁量权）。

### 2.4 页面流（UI 三处小改动）

| 角色 | 页面 | 能力 |
| --- | --- | --- |
| safety | 报告页新增「派发」区 | 选/确认责任人 + 设定 deadline → `dispatch` |
| responsible | 新增「我的整改单」页 | 列出被派工单 → 填写说明 + 拍照上传 → 申请验收 |
| admin/safety | 管理端新增「验收队列」 | 核对照片与说明 → 通过(closed)/驳回(rejected) |

### 2.5 催办与逾期巡检（复用 notify_service 通道）

- 扫描逻辑独立为纯函数 `scan_overdue()`：逾期未销项 → 推送责任人本人
  （企业微信/钉钉，文案含单号与逾期时长）；逾期满 24h 未响应 → 升级推送
  admin（分级越级）；
- **两种驱动方式（刻意不依赖 Web 进程内常驻定时）**：
  - **演示版**：管理端「扫描逾期并催办」按钮 + 时间游标参数（可把指定工单的
    deadline 拨到过去），现场即时触发一轮完整扫描——故事线节奏可控，
    无需真等小时级时间；
  - **生产版**：`scripts/overdue_scan.py` 由系统 cron 调用同一函数，调度与
    Streamlit 进程生命周期彻底解耦；
- 推送留痕进 `notification_logs`，审计动作 `dispatch/submit/approve/reject/escalate`
  全部落 `audit_logs`；
- 备注：并非 Streamlit 刷新会杀进程线程——`monitor_service` 的 daemon 轮询
  （`monitor_service.py:74`）即常驻反例；选按钮/cron 是为了**演示时间可控**
  与**调度不绑定 Web 进程生命周期**两个更硬的理由。

### 2.6 测试与验收标准

- 新增 `tests/test_work_order_flow.py`：派发→提交→驳回→再提交→验收全链路；
  逾期派生状态边界；越级触发（mock 时间）；权限负例（responsible 不能看他人工单）；
- 全量回归 123 passed 不破坏；
- 现场演示脚本：张三检出火花 → 自动派给李四 → 李四逾期（用「扫描并催办」
  按钮 + 时间游标触发，见 2.5）→ 升级提醒 admin → 李四整改提交 → 张三验收销项。
- **备选分支 A**（P2 文字上报落地后）：安全员口述文字隐患 → 确认卡片 →
  进入同一套派发流水线——体现"人工线索与机器感知汇流"；
- **备选分支 B**（P3 落地后）：指令框查询工单状态、统计周报——体现任务指令通路。
- 台账列表需展示 `tasks.source` 来源列（camera/upload/text），答辩话术：
  "机器发现的隐患和人工上报的隐患在同一台账里统一流转"。

预估工作量：schema+角色+规则 ~0.5 天；三个页面 ~1 天；催办+测试 ~1 天，合计 2~3 天。

## 四、P2：自然语言上报层（混合 Provider：可选云端 Key + 本地兜底）

> 对标结论：案例的「文字/语音上报」= 自然语言 → AI 提取结构化信息。本项目现有
> 文本输入仅为作业票结构化字段，**自由文本/语音的上报路径缺失**；且大量隐患
> （无证上岗、无交底、通道被占）不来自画面，必须给人工发现的问题一个入口，
> 与视觉检测合流到同一派发流水线。
>
> 路线决策：**双 Provider 架构**——配置了兼容 OpenAI 接口的 API Key 即用云端
> 强模型（提取质量对齐案例、ASR 免本地打包）；未配置则维持现状/落本地 Ollama。
> 离线能力始终是一等公民，云是可选增强——与 Ollama 现有的「可选增强、断网降级」
> 定位（README Q8）同一模式，架构上只是给既有插槽多接一个 provider。

### 4.1 信息流与人机分工

```
文字框（直敲 / 语音→ASR 回填） ──► AI 提取四字段 ──► 安全员确认页 ──► create_task
        ▲ 可选云端Key | 本地Ollama | 手填           ▲ 可改可否（人眼把关）
                              只做草稿生成,不做判定
```

- AI 执行**受限槽位提取**：只输出 {位置、隐患描述、建议场景、建议类别} 四个固定字段；
- 安全员确认后才 `create_task`，之后与图片上报在派发侧完全合流（复用 P0 规则）。

### 4.2 四条硬约束

1. **默认关闭、显式开启**：`llm/asr.provider=openai_compat` 且配置 key 才启用；
   走云端的功能在 UI 有 ⛅ 标注并提示「该功能将发送内容至外部服务」。主叙事
   永远是「可完全离线运行」，云只增强；
2. **护栏与 provider 无关**：`建议类别` 必须命中 `compliance.severity` 既有的
   隐患键集合，命不中整条作废；安全员确认环节无论强弱模型一律保留——判定路径
   依旧零 LLM（Q3/Q6），风险定级只在融合 Agent 规则矩阵发生；
   **文字类任务不进五 Agent 链路**（无影像可推理、无票可核），其初始风险等级由
   安全员确认后的「建议类别」键直接查 `compliance.severity` 映射得到——定级
   依旧是纯规则查表；与影像任务在**工单台账之后**（派发/跟进/周报）完全共享，
   推理过程各自独立：`tasks.source = camera/upload/text` 仅作来源标注。
3. **统一降级链**：云端失败（断网/欠费）→ 本地 Ollama → 手填表单，逐级自动回退
   并记日志，三档是递进兜底而非并列系统；**两档皆无时**：文字上报恒为手填表单
   （v0 即完全体，仅失去预填便利），语音按钮灰显并提示开启路径，P3 意图识别
   跳过 LLM 层由规则+人工确认兜底；界面明示「AI 提取不可用」，不做静默变傻；
4. **范围收敛**：key 仅用于文本提取与语音转写两个新入口；视频帧/原图永不出场，
   工单润色 `polish()` 继续走本地 Ollama 不扩面。

### 4.3 提取效果评测（保留）

准备 30~50 条真实风格隐患描述的小测试集，分别测本地 Ollama 与云端两种 provider
的四字段命中率写入评测材料——顺带成为「本地可用性」的实测论据。

### 4.4 关于「统一交互窗口」的决策

对标案例架构图的实质：文字/语音/图片/工单查询是**四个并列入口**，统一的是
后端管线与工单台账，而非一个对话框（其对话感来自 Coze 平台原生形态）。
本项目采纳其实质、不搬其皮肤：

- ✅ 做「统一上报面板」（P2 内，约半天）：**在现有「上传与作业票」页原地升级为
  三个 `st.tabs`（互斥显示，各独占整页）**——Tab①影像研判（现有能力原样迁入，
  作业票字段收纳为可选展开）、Tab②文字/语音上报（新能力）、Tab③工单速查；
  侧边栏导航位置与数量不变。三种入口提交后均走 `create_task` → 派发管线；
- ❌ 不做全站对话窗口：实时监测是持续刷新仪表盘（红框/声音/轮询）、图片研判
  是标注框网格，均不适合聊天气泡形态；且"告警当帧即出、无多帧门控"的轻链路
  叙事本身依赖专用界面（README Q1/Q2）；
- ⚠️ 不学其「责任人推荐置信度 95%/82%/71%」：LLM 拍出的置信度不可审计，
  与本项目"派发查确定性映射、定级查规则矩阵"直接相反，答辩可作为对照差异点。

### 4.5 实施拆解

1. provider 抽象（适配现有 `llm_engine.py` 模式：不可用即返回 None）+ 文字链路；
2. 云端 ASR 接入（免 faster-whisper 打包；本地 faster-whisper 作为无 key 时的
   可选安装项，缺失则隐藏语音入口）；
3. 录音不落盘（音频仅转写即焚）、提取结果与降级链路全量审计留痕。

预估：文字链路+provider 抽象 1~1.5 天；云端 ASR 0.5 天；本地 ASR 可选项 0.5 天。

### 5.1 双链路落地三约束（外部评审吸收，已对照代码核实）

架构共识：多模态素材走自研重链路；文本语音经意图识别分发到生成工单/查库等动作。
落地钉死三条：

1. **启动预热 + 单例锁（首请求成本前移）**
   现状核实：ORT 会话已有进程级缓存（`yolo_engine._SESSIONS`），不存在重复加载；
   缺口在首次会话创建仍发生于首个用户请求。行动：登录后预热线程扩容至双场景
   检测头构建；`page_realtime` 的 `st.cache_resource` 在非脚本线程会绕过缓存，
   改为模块级单例+锁（同 `monitor_service._MONITOR` 模式）供预热与页面共享；
   预热完成后启动脚本打印「YOLO 双场景模型预热完成」日志，既方便排障，
   也为答辩提供"模型前置预热、消除首请求卡顿"的启动日志截图证据。

2. **双链路共享统一会话上下文（防"看了视频却开不了单"）**
   地基已具备：研判结果按 `task_id` 全量持久化（save_result→agent_runs/risks 等），
   `session_state.current_task_id` 即"最近任务"指针。新增机制：
   - 意图路由支持**引用型槽位**：「把刚才的检测结果生成工单」→ 解析为
     `current_task_id` → 从库读回检出+风险等级组装工单（复用处置 Agent 落库路径）；
   - **告警→工单桥**：实时页高危告警现仅落 `alarm_events`，P0 扩展
     「voice『给刚才这个红框开整改单』」路径，打通轻链路产物进派发流水线。

3. **全分支耗时埋点 + 等待可见性**
   重链路已有 `agent_runs`（逐 Agent status/cost_ms）与进度推送；补齐意图识别、
   工单生成两条新分支的同款计时日志；前端对所有 >300ms 的操作区分提示
   （视频解析中/意图识别中/查询中 spinner 文案），杜绝无响应黑框观感。



### 5.2 意图识别的准确性保障（四层防线，不引重框架）

架构上前置说明：图片路径**没有**意图识别（上传即研判，无歧义）；三 Tab 的
UI 契约本身就是第一层意图声明，真正的识别器只服务自由文本中极少数跨界输入。
四层防线由廉到贵：

1. **架构消歧**：在哪个框输入即什么意图（上报框/速查框），多数输入不进识别器；
2. **规则兜底**：关键词+正则（「查|进度|多少|统计」+`\d+号` → 查询；
   其余默认上报），确定性、可单测；
3. **LLM 封闭集分类**：规则不确定才调一次本地 qwen3:8b，输出限定
   `{"intent": "report"|"query"}` 并白名单校验，不在集合内即作废；
4. **问一次人**：仍不确定则按钮确认，误判被人机交互吸收，不带错意图入系统。

配套：30~50 条真实话术测试集实测意图准确率，随提取命中率一并写入评测材料；
**测试集以 JSON 形式落库 `tests/datasets/` 并纳入版本管理**（文字上报提取用例、
意图识别用例各一份），配脚本一键跑评测输出命中率指标，避免散落在开发者脑中。
明确不引入 LangChain/function-calling 框架：意图空间是封闭小集合而非开放工具
调用，~80 行 `TextIntentRouter`（正则表+可选 LLM 调用+JSON 校验）即可，
延续 README Q9 的既定论证（确定性优先、可审计、零新增依赖）。

**读写硬隔离（安全边界）**：`TextIntentRouter` 仅处理**只读意图**（查询/统计/
报表）；一切写操作（建单、派发、验收）必须经对应 Tab 页面的人工确认按钮触发，
意图模块禁止调用任何写服务——自由文本入口天然暴露于提示注入与参数污染，
用"查询归查询、上报归上报"的结构性隔离根治，而非依赖规则枚举去堵。

规则层的实现要点：**不做"理解"，只做参数抽取**（工单号/状态词/时间词/类别词
四类封闭模式），抽到的参数直接调用现有服务方法；参数缺失按粒度退化——全参直
达详情卡、部分匹配列候选让人一次点选、零参退化为筛选列表（即传统工单交互）。
执行端恒为手写方法，杜绝理解偏差与注入风险；正则用例表即单测集。
