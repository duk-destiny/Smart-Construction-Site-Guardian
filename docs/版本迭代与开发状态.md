## v0.1 · 感知与研判基线

**定位**：把"看得见、判得准、留得下证据"做扎实。

- 双场景本地检测：动火作业（火花/烟雾/灭火器）、施工 PPE（五类目标），
  YOLO ONNX CPU 推理，双头并行 ~211ms/帧；
- 上传研判重链路：视觉 ∥ 规范 RAG → 融合 → 复核 → 处置，≤8s 预算内超时降级；
- 实时轻链路：首帧 critical 当帧出警 + 截图留证 + 异步推送 + 后台轮询冷却去重；
- 数据闭环（本项目独有）：人工纠偏 → 审核 confirmed → 回写训练集 → 复训 → 注册/切换；
- 安全治理收口于 v0.1 冻结前：连接泄漏、RTSP 持久连接并行抓帧、审计注入、登录限速、
  评测线上一致阈值口径。

已知边界（当时即明确登记）：工单生成后**没有去向**——无责任人、无流转、无销项，
`work_orders` 的唯一 UPDATE 是文案回填。这是 v0.2 的全部动机。

### 设计决策记录（答辩追问点）

1. **「逾期」为何不入库**：deadline 与 status 足以推导，派生态避免扫描线程反复刷库，
   也规避"逾期了但刚被驳回"的状态机歧义；
2. **演示为何用时间游标而非真定时器**：故事线需要可控节奏（评委面前等一小时不可行）；
   Web 进程内常驻定时在重启后丢失且无法补跑，cron 脚本 + 手动按钮双入口天然覆盖两场景；
   注：Streamlit 刷新并不杀 daemon 线程（monitor_service 为证），理由是可控性与解耦，
   不是线程存活问题；
3. **老库 CHECK 约束迁移**：SQLite 不能 ALTER CHECK。采用暂存依赖视图→建新表拷贝→
   DROP/RENAME→重建视图的标准变体，临时 PRAGMA foreign_keys=OFF 且逐步 commit；
   已用内存库模拟 v0.1 结构验证：账号密码无损、lisi 自动出现、重复执行幂等；
4. **读写硬隔离前置**：responsible 页面的所有写入都由显式按钮触发，意图/对话层
   （P3）被禁止调用任何写服务——自由文本入口的结构性注入面从一开始就不存在。

### 兼容性

- 老演示库直接升级：首次启动自动完成 CHECK 重建 + 补种 lisi + 全部新列 ALTER；
- 新克隆：schema.sql 直接带全量定义，零迁移发生；
- 对既有调用方零破坏：`create_task` 新增 source 参数带默认值，全量测试佐证。

## v0.3 · 风险周报（P1 落地纪实）

**目标**：补齐闭环的复盘层——把 v0.1 的检测事实与 v0.2 的处置台账合并成
可归档、可汇报、可追责的周期报告（对标案例「按风险等级汇总周报辅助决策」）。

- **服务** `services/report_service.py`：`gather()` 三源确定性聚合 +
  规则化结论行；`render_pdf()` fpdf2 中文渲染（SimHei/Noto/WQY 候选表复用）；
  `generate()` 编排 + 审计。
- **UI** 管理端「风险周报」区块：日期区间 → 指标卡/结论/责任人进度表预览 → PDF 下载。
- **运维** `scripts/weekly_report.py`：cron 归档入口，系统调用豁免 UI 权限门
  （沿用 ExportService 语义），登录态仍强制 export 并写 `report_generate` 审计。
- **测试** 8 例固定日期种子；过程中修出 fpdf2 multi_cell 游标陷阱
  （默认落右边界，长文连排必炸——全部显式 LMARGIN/NEXT 收口）。

### 设计决策记录

1. **逾期率口径**：责任人画像中"存量逾期 ÷ 该责任人周期内派发总数"，
   分母取派发而非在办，避免"干完一单清零掩盖历史拖期"，数字对督办更有约束力；
2. **CLI 免登录门**：cron 属运维侧操作，无用户会话概念；权限边界仍在 UI 层
   （管理端按钮走 export 校验），两层语义清晰不混用；
3. **PDF 不内嵌图片证据**：v0.3 只做统计叙事，现场照片已存档案目录并在
   验收队列按单查阅，避免报告体积失控（可作为 P2 加分项再评估）。

## v0.4 · 统一上报三 Tab + 可选语音（P2 主体落地纪实）

**目标**：给"摄像头拍不到的隐患"开正式入口，实现双通路架构中的任务指令通路
（本版先落"创造类"：文字/语音建单；读取类对话路由 P3 留待下一步）。

- **三 Tab 原地升级**（方案 4.4）：影像研判原样迁入 / 文字上报 / 工单速查只读列表；
- **文字链路** `create_text_hazard`：severity 白名单（safe 正向信号拒绝）→
  critical/warning 映射风险等级 → 复用处置 Agent 模板文案 → source='text'
  直接进入既有派发闭环——即报告页派发面板、我的整改单、周报责任人画像
  对文字来源**零改动生效**；
- **语音最小化按用户裁决执行**：仅 OpenAI 兼容转写调用一次，无 whisper、
  无 MP3 上传；未配置时 UI 整块静默不渲染；
- 测试 9 例；上传页标题更名为「统一上报」。

### 设计决策记录

1. **白名单锚定 severity 表而非硬编码**：隐患下拉直接读运行时合并后的
   `compliance.severity`，管理员改配置即增删可报类别，延续数据驱动纪律；
2. **文字单定级不入规则矩阵辩论环节**：矩阵面向"检测目标组合"，文字单只有单一
   类别——直接 critical→较大 / warning→一般 两档映射，保守且可解释；
3. **语音失败不吞描述**：转写失败保留 last_error 轻提示，文本框仍可用，
   断链路永不超过"回到手填"这一层。

## v0.5 · 对话式查进度（P3 落地纪实）

**目标**：兑现"任务指令通路"的读取半边——自然语言查工单/逾期/统计，
全程只读。设计依据方案文档 5.1/5.2，实现零偏离。

- **服务** `services/intent_router.py`：`extract` 纯函数抽参（可单测）；
  `route()` 分层决策；`detail_view/list_view/overdue_rows` 只读执行器
  （全部走既有 DAO/SQL）；
- **口语序数映射**：真实工单号为随机后缀，「3号工单」按**创建时间最新序**
  解析为具体单据——演示里不用背哈希；
- **LLM 兜底**：`LlmEngine.ask_json`（/api/chat + 严格 JSON + 白名单校验），
  未配置 Ollama 时该层整体跳过，规则+人工点选即完整可用（v0.2 静默约定的延伸）；
- **UI** 速查 Tab 对话化：问一句 → 详情卡 / 消歧点选 / 逾期清单 / 概览四指标；
- **测试** 10 例，其中"多轮会话前后 audit_logs/work_orders 行数零变化"
  是读写硬隔离的自动化铁证；越白名单 LLM 输出被白名单校验拒收的分支覆盖。

### 设计决策记录

1. **序数语义取最新序而非 ID 字典序**：现场口吻"最新那张/3号那单"天然是
   时间序；ID 哈希不可口述，此映射是演示可用性的关键一步；
2. **越白名单即弃**：LLM 输出 intent 不在 {order_status, order_search,
   overdue_stats, weekly_stats, overall_stats, null} 直接整包丢弃回人工层——
   与 P2 白名单同构，注入面为零；
3. **不做写意图**：「把刚才那条生成工单」这类引用型**写**指令依旧只在
   报告页派发面板以按钮形态存在（v0.2 桥），路由层永远只读——答辩时这是
   "为什么对话不能替你开单"的标准答案。

### 决策记录

## v0.7 · 🟢 计划内清尾（纪实）

- **评测集资产化**：`tests/datasets/`（提取30/意图30）+ `eval_datasets.py`
  一键命中率 → `data/eval/dataset_eval.json`。实测：意图 30/30=100%
  （规则离线）；提取 core 63.3%/位置 0.3（本地 8B 实测，云 key 通道已备）。
  评测轮反哺修复意图路由三处真缺陷（中文边界 、周时间窗、闭环正则系）；
- **告警→工单桥**：管理端告警卡片一键转换，severity 查级、source=camera、
  审计流水幂等守卫（实时告警 task_id=None 的正确姿势），6 例测试；
- **量化评测**：fire_v2/ppe_v3/ppe_v4 全部产出 INT8 副本（44.7→11.5MB，3.9x）
  并注册 active=0；逐类对比表见 data/eval/model_eval.json（运行记录
  data/eval/run_v07.log）。达标前维持 active=0 不顶替。

### 量化评测结论（逐类 F1，configured 阈值，独立测试集）

| 模型 | 类别 | FP32 | INT8 | Δ |
| --- | --- | ---: | ---: | ---: |
| fire v2 | 烟雾 | 0.909 | 0.909 | 0 |
| fire v2 | 火花 | 0.794 | **0.725** | -6.9% |
| ppe v3 | 佩戴安全帽 | 0.870 | 0.864 | -0.6% |
| ppe v3 | 未戴安全帽 | 0.732 | **0.762** | +3.0% |
| ppe v3 | 未穿反光衣 | 0.755 | **0.706** | -4.9% |
| ppe v3 | 人员 | 0.620 | 0.586 | -3.4% |
| ppe v4 | 未戴安全帽 | 0.791 | 0.791 | 0 |
| ppe v4 | 人员 | 0.540 | 0.515 | -2.4% |

**结论：INT8 维持 active=0 不切换。** 多数类 ±1%，但火花 -6.9%、未穿反光衣
-4.9% 的类级损失超出 README 原预估（<0.5%）；量化副本定位为**体积敏感的
边缘部署选项**（44.7→11.5MB，3.9x），精度敏感的线上继续 FP32。
这组实测数字本身就是"注册→评测→手动切换"闭环价值的最好答辩证据。

### 设计决策记录（答辩追问点）

1. **首登强制改密为何默认关**：种子账号是演示故事线的一部分
   （评委按 admin/admin123 登录），强制改密会打断演示；故做成
   `security.force_default_pwd_change` 门控——默认顶栏常驻提醒，
   生产一键开启强制；
2. **审计删档为何默认禁用**：`audit_logs` 仅追加（触发器双保险）是
   C4 卖点；留存归档默认只导出 CSV 不删行，`--delete` 需显式追加，
   且删前必须行数校验一致 + 写 `audit_archive` 凭证 + 原样重建禁删
   触发器——删档行为本身留在不可篡改的审计里；
3. **文件名消毒为何收口到一个函数**：v0.1 的 evidence.py 早已做对
   （正则压制+截断），但 page_admin/page_upload 没复用同一纪律；
   v0.8 收口为 `sanitize_filename()` 单一入口并回归测试钉死
   （绝对路径/盘符/`../`/纯点/中文不误伤）；
4. **派发推送复用告警通道而非新建**：与 v0.6 催办同构——
   notification_logs.alarm_id 本就是软引用，`wo_<id>` 前缀区分消息族，
   通道配置零增加；未启用 skipped 留痕，主链路零耦合。

### 兼容性

- 老演示库直接升级：users 两列自动 ALTER；既有账号（含密码、角色）
  不受补种影响，仅新种子账号带初始密码标记；
- `get_progress`/`pop_async_result` 不传 user_id 保持旧行为（内部调用
  与既有测试零改动通过）；
- `_push_sample` 收拢后 `push_overdue`/`test_push` 对外语义与返回结构
  不变（skipped 补齐 error 键为增量）。
