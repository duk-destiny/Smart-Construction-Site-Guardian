# 08 · 设计取舍 QA

> 返回 [README](../README.md) · 上一节 [07 部署与生产安全](07_部署与生产安全.md) · 下一节 [09 后续优化计划](09_后续优化计划.md)

> 下面这些「为什么这么设计」的问题，答案都能在代码里找到依据，不是话术。

## Q1 为什么分「上传研判重链路」和「实时监测轻链路」两条路？

两条链路的优化目标根本不同。上传态追求**研判深度**——五段流水线协同、RAG 条款引用、证据链落库、工单闭环，可以接受 3–8s；实时态追求**告警时效**，首帧 `critical` 必须当帧出红框+告警。`core/realtime_engine.py` 的 `analyze()` 注释写死了实时不变量：「analyze 与告警之间不得插入 LLM/RAG/工单等阻塞推理，首帧 critical 即返回，无多帧确认门控」。用一套链路同时满足两个目标，必然两头不讨好。

## Q2 实时轻链路为什么没必要接入研判流水线编排或大模型？

- **帧率预算**：实时每帧只有几十 ms 预算，LLM 单次生成秒级、RAG 检索百 ms 级，塞进去直接打穿「采样节奏 ≠ 告警 SLA」，事故发生了告警还没出；
- **确定性优先**：实时态要的是「检出 spark/smoke → critical → 出警」这种 100% 可重复的判定，不是创造力；LLM 的「润色」对告警判定零增益，反而可能把置信度 0.3 的火花判成「安全」；
- **编排开销×帧率=纯浪费**：流水线编排是为一次性深度研判设计的重设施，每帧跑一次编排等于把固定开销乘以帧率；
- **代码佐证**：`realtime_engine.py` 全程不 import `llm_engine`/`rag_engine`/`pipeline`，`analyze()` 只调 `core/compliance.py` 的 `evaluate()`（纯规则查表）+ `core/false_positive.py` 过滤 + `core/tracker.py` 跟踪。需要「说人话」的处置建议，已在告警落库后异步做（`pipeline/action.py` 的 `polish()` 后台线程），不阻塞帧。

## Q3 上传链路里，融合段和复核段为什么不引入 LLM？

这两个环节做的是**影响处置动作的硬决策**，必须可解释、可审计、可复现，而 LLM 天然不可解释：

- **融合定级段 FusionStage**（`pipeline/fusion.py`）：职责是「查风险矩阵取最高等级 + 误报过滤」，是查表 + 阈值比较（`core/false_positive.py` 的 PPE 矛盾框/烟雾-反光衣冲突）。LLM 在这里只会引入幻觉，把确定性的「spark 置信度 0.3 < 0.55 → 判光斑误报」变成不可预测的猜测；
- **复核段 ReviewStage**（`pipeline/review.py`）：判定逻辑是确定规则（`cls ∈ HIGH_RISK_CLASSES` 且 `conf < 0.55`）。规则没覆盖的本来就该交人工，让 LLM 拍板「要不要复核」反而增加不可解释性、模糊审计边界；
- **安全系统铁律**：定级、是否复核这类硬决策用规则；LLM 只做不影响判定的软任务。两段全程无 `llm_engine` import。

## Q4 LLM 到底用在哪？为什么不进判定路径？

LLM 统一走 `core/chat_client.py` 单一入口（云端优先四级降级），只承担**不影响判定的生成/分类类任务**：

1. 认知层的规划与汇总（Plan-and-Execute 受限范式：模型决定「调哪些工具、调几次」，每个工具内部仍是确定性实现，参数过 args_schema、结果过返回白名单）；
2. 处置段（ActionStage）工人提示润色（`polish()`，工单落库后异步、模板兜底，不参与定级）；
3. 表单预填提取（`enhance_service`，越白名单即弃、仅作草稿人工确认）；
4. 意图路由封闭集分类兜底（`intent_router._ask_llm`，白名单校验）。

铁律：风险定级（`compliance.severity` 查表）、是否复核、误报过滤等硬决策一律规则；副作用动作（建单草稿/告警建议）强制人工确认、无豁免开关。LLM 全灭时系统按四级降级可控衰减（`degraded ≠ failed`），判定与告警链路零依赖 LLM。

## Q5 视觉与规范为什么要并行 + 两阶段 RAG？

- **并行**：视觉 3s / 规范 4s 用 `ThreadPoolExecutor` 并行 `submit` + `future.result(timeout)` 精确超时，总链路压在 ≤8s，超时转 `degraded` 不崩进程（`pipeline/orchestrator.py` 的 `_safe()`）；
- **两阶段 RAG**：规范检索段一阶段只查作业票字段（快），拿到视觉违规描述后再补一次 RAG 条款检索（视觉 `violation_descs` 回灌 `rule`）。避免每张图都跑一次完整规范检索，`skip_rag` 标志控制是否触发第二趟（`pipeline/rule.py`）。

## Q6 误报过滤为什么用规则而不是让 LLM 判别？

`spark` 低置信光斑、PPE 矛盾框（同一人既 `helmet` 又 `no_helmet`）、烟雾-反光衣冲突，都是确定性的逻辑冲突，规则秒判且可解释；LLM 逐帧判误报会吃掉帧率预算，还会把可解释的「为什么过滤」变成黑盒。代码在 `core/false_positive.py` 的 `filter_ppe_contradiction` / `filter_smoke_vest_conflict`。

## Q7 模型切换为什么不自动顶替线上、要手动确认？

安全系统里新模型 mAP 提升不等于所有现场场景都更优，自动顶替有回退风险。当前设计：复训完 `register(active=False)` 不立即激活 → 展示新旧 mAP 对比 → 人工「一键切换」 → `model_service.switch()` 唯一落 DB（`model_registry.active`，v0.9 起不回写 config.yaml）+ 引擎热加载，留出对比和回滚窗口（见 `ui/page_admin.py`）。

## Q8 为什么每个选型都偏「轻量」？（Ollama / ONNX / BGE+Chroma / React / SQLite）

项目定位是「工地一线、单机部署、判定与数据本地化」的安全智能体——模型推理与数据链路必须断网能活，LLM 认知通道走云端、断链自动降级。每个选型都对应场景硬约束：

| 约束 | 选型 | 佐证 |
| --- | --- | --- |
| 网络（断网常态） | 推理/检索/存储全本地；LLM 云端优先 + 降级链 | `llm_engine.py` 只与 localhost:11434 通信、`rag_engine.py` 全本地、`yolo_engine.py` 纯 onnxruntime |
| 硬件（无 GPU） | ONNX Runtime、BGE-small、SQLite 全 CPU-friendly | 双头并行 ~211ms（`_compute_intra_op()` 防抢核） |
| 实时性（首帧秒级出警） | 本地推理 + 规则当帧即出；云端往返 2-5s 不可接受 | 告警链路纯规则无外部依赖，断网也能出红框 |
| 数据主权 | Embedding/检索/存储全本地；云端 LLM 仅接收文本上下文 | 视频帧与检测原始数据不外发；工具白名单 + 参数 schema + 返回白名单三重护栏 |
| 安全容错 | 轻量组件各自独立，全有确定性降级路径 | LLM 挂走模板、BGE 挂跳 RAG、权重缺跳该头，系统不因可选组件缺失而瘫痪 |

前端选 React + Vite + AntD：多角色工作台的组件化/路由/状态管理需求超出 Streamlit 表达力；构建产物由 FastAPI 静态托管、单进程单端口；Streamlit 经典版保留为回退入口（与 React 复用同一 services 层，零业务复制）。早期 v0.x 选 Streamlit 是为最快闭环「拍照→检测→告警」，Gradio 缺摄像头轮询与会话级状态。

## Q9 为什么流水线编排和认知层是手写，而不用 LangChain / LangGraph / AutoGen？

1. **DAG 是定长静态直链**：链路固定为 `[视觉 ∥ 规范] → 融合 → 复核 → 处置`，无循环、无条件分支、无工具调用循环。LangGraph 的核心价值（状态机 + 循环 + 人在回路）对一条直链是杀鸡用牛刀；手写 `ThreadPoolExecutor` + 超时降级二十来行就够。
2. **确定性优先于「智能」**：定级、复核是硬决策用规则，全链路零 LLM 介入判定；LangChain 的核心抽象（Tool / ReAct / Memory）是为 LLM 动态决策设计的，引入它就得背一套 prompt 编排、token 计费、可观测栈。
3. **可审计、零魔法**：`pipeline/base.py` 用 `StageBase` ABC + `StageMessage` dataclass 信封，强制「禁止裸 dict 跨段传递」，每个节点的 `status`/`cost_ms`/`error` 都可落库追溯；`_safe()` 把超时/异常统一转 `degraded/failed` 不崩进程。这套契约不到 60 行、行为完全可见；换框架后出问题要先翻框架源码定位是哪一跳挂了——对安全系统是不可接受的调试成本。
4. **依赖与部署更轻**：`requirements.txt` 零 langchain/langgraph/autogen/crewai 依赖。

> 一句话：编排就是「并行 + 超时降级 + 异常兜底」三件套，标准库即可表达；框架解决的是「LLM 动态决策的复杂性」，而本项目恰恰把 LLM 关在判定路径之外，所以手写更短、更可控、更可审计。

## Q10 人工纠偏的具体流程是怎样的？多次复训会不会重复堆积、污染源数据集？

闭环五步（每一步都在代码里有据可查）：

1. **采集**（`ui/page_report.py`）：人工改判（`override`）与逐目标纠偏（`detection_fix`，工作台标误报/修正类别）写入 `feedback_samples`，初始 `pending`，需 override 权限；
2. **审核**（`ui/page_admin.py`）：逐条改状态 `pending/confirmed/rejected`，可展开可视化复核再修正，一键导出 CSV。**只有 `confirmed` 才进训练**；
3. **生成 YOLO 数据**（`core/feedback_dataset.py`）：先过滤 `status != "confirmed"`，再按检测类别自动归场景（fire/ppe），复制图片 + 写统一类别标注到 `data/feedback_training/yolo/<scene>/`；
4. **并入统一训练集**（`scripts/prepare_combined_dataset.py`）：`fb_` 前缀纠偏源与 `data/raw` 各原始源合并到 `data/combined/<scene>/`；
5. **复训**（`scripts/train_combined.py` / 管理端复训按钮）：合并集训练 → 导出 ONNX → `register(active=False)` → 管理端一键切换 → 回写 config + 热加载。

**不会重复堆积**：合并幂等，`_prepare_spec()` 按目标文件名判重（纠偏样本文件名 `{scene}_{task_id}_{id}.jpg`，`task_id + id` 唯一，重复跑只记 `already_exists` 跳过）。
**不会污染源数据集**：纠偏数据只写生成目录 `data/combined/`，永不回写 `data/raw/`（合并脚本只读）；`pending/rejected` 在第 3 步即被过滤。

> 一句话：纠偏 → 审核（confirmed）→ 生成 YOLO → 幂等并入 combined → 复训；源数据只读、重复跳过、未审核不进，闭环安全。


## Q11 已经有统一对话入口了，为什么影像研判还要单独一个入口、单独一条链路？

两者是**「问」与「办」两种交互形态**，共享同一套引擎，不是两套实现：

- **产物形态不同**：影像研判的产物是结构化业务对象——检测框、逐条合规结论、风险定级、工单草稿、`agent_runs` 证据链，要落库、要派发、要人工改判；对话的产物是一段回复文本。页面承载表单上传（multipart + 魔数校验 + 大小上限）、异步研判（`start_async_run` 后台线程 + 进度轮询）、结果卡片与证据链时间线，这些交互形态对话窗口装不下；
- **预算形态不同**：上传研判是 ≤8s 墙钟预算的一次性重任务，允许异步等待；对话是来回追问，视频分析走 `run_video_pipeline` 工具时可传 `mode=quick` 跳过二阶段 RAG 提速追问（`pipeline/orchestrator.py` mode 参数），保证追问节奏；
- **引擎层已经统一**：v2.1 起认知层可直接经 `run_video_pipeline` 工具触发同一条流水线（检测结果按文件 hash 进程内缓存，多轮追问不重跑检测）——**两个入口、一个引擎**，判定逻辑零复制。

## Q12 为什么不用大模型自带的多模态能力（GPT-4o / Qwen-VL 直接看图）做检测？

> 先说清"多模态智能体"的口径：本系统的多模态指**感知多模态**——文本、图片、视频、实时流都进同一套智能体闭环（视觉是眼睛、LLM 是大脑、工具是手脚）；与"用多模态大模型看图判定"是两回事，见下。

- **可复现性是硬要求**：安全定级必须可复现、可审计、可回归评测。多模态大模型同一张图两次推理结论可能不同，没有稳定的检测框坐标与置信度，`evaluate_models.py` 的逐类 F1 基线无从建立，也无法在纠偏复训后做 A/B 对比；
- **数据主权**：本项目 C1 约束明确「帧与检测原始数据不外发」——云端 LLM 只接收文本上下文（描述/统计 JSON），工地影像绝不进云。多模态方案要把每一帧送上云，直接打穿这条线；
- **时延与成本**：YOLO ONNX 本地 CPU ~211ms/帧且零边际成本；云 VLM 秒级 + 按 token 计费，实时 2fps 多路摄像头的成本与时延都不可接受，断网即全瘫；
- **长尾场景反而不如专模型**：通用大模型没见过本工地的反光衣样式/摄像机机位，小目标（远距离安全帽）召回天然弱；自训练模型配纠偏闭环能在自家场景数据上持续变准，通用 VLM 做不到；
- **边界说清楚**：不是否定 VLM——不影响判定的生成类任务（复核辅助理解、文案润色）走 LLM 是合理的，但**判定链路的输入必须是确定性检测器的结构化输出**，这是 `chat_client` 只见文本、`yolo_engine` 纯 onnxruntime 的架构事实。

## Q13 认知层的执行计划是 LLM 生成的，怎么防止它规划出越权或危险操作？

四层防线，全部在代码里强制，不依赖提示词自觉：

1. **工具白名单**：计划解析后过 `kernel.validate_plan_obj`——pydantic 校验 + 工具白名单核验，计划里出现注册表之外的工具或越界参数直接 `ValidationError`，解析失败重试 ≤1 次即落失败态，绝不让 LLM 续写补全；
2. **副作用强制挂起**：`raise_suggestion / create_order_draft` 标记 `side_effect=True`，内核遇之置 `pending_confirm` 等人工确认，无豁免开关；人工「改计划」也要过同样的白名单校验（同一 `validate_plan_obj` 入口）；
3. **作用域不经 LLM**：用户身份/角色由代码经 `ToolCtx` 注入，LLM 无法伪造调用者身份；只读工具同样执行 `require(user_id, "view")` 数据权限；
4. **步数与预算双闸**：计划 ≤8 步 + 墙钟总预算，触顶强制收敛降级汇总——不存在「无限循环调用工具」的通路。

## Q14 对话回复和周报里的数字/条款，怎么保证不是 LLM 编的？

- **周报数字强制溯源**：`weekly_report` 剧本要求规划第一步调 `weekly_report_data` 工具（确定性 SQL 聚合，零 LLM），汇总文本中每个数字必须标注来源键路径，代码侧 `stats_fn + validate_fn` 回溯校验 100% 对得上才放行，二次不达标整体落模板档——LLM 只负责把已核验的统计数字组织成人话，不负责产生数字；
- **条款必须可回溯**：规范引用只来自 RAG 检索命中的原文条款（BGE + Chroma，带来源文档），而不是模型记忆；`rag_search` 工具检索失败降级返回空集，回复里就不出现条款，宁缺勿编；
- **会话摘要零 LLM**：`build_digest` 由代码模板拼接（≤300 字），状态/耗时/错误都是真实执行记录。

## Q15 为什么对话不能直接写库、自动开单？AI 不是应该全自动闭环吗？

- **高后果场景的人机边界**：建单/派发/验收会触发对人的责任指派与催办推送，误操作的代价由现场工人承担；因此**读写硬隔离**——对话层永远只读（v0.5 起「整轮会话零 INSERT/UPDATE」有自动化测试铁证），写操作只存在于有权限门 + 审计留痕的页面按钮；
- **想写也写得「半截」**：对话里的写意图只能落成**待审队列**——副作用工具产物（工单草稿/整改建议）进 `pending_confirm`，人工确认后才走既有建单流程，且草稿不带风险定级（定级由人工确认时查 `compliance.severity` 表）；
- **这不是能力缺陷而是产品决策**：全自动开单演示效果好，但把「AI 判断」直接变成「对人的处罚依据」在安全领域不可接受——评审追问「为什么不让它自动建单」时，答案就是上面两条。

## Q16 工地影像和检测数据会外发吗？数据边界在哪里？

- **推理与存储全本地**：YOLO ONNX、BGE Embedding、ChromaDB、SQLite 全部本地进程/本地盘，视频帧不出主机；
- **云端 LLM 只见文本**：`chat_client` 上行的只有文本上下文（用户问题、统计 JSON、条款片段、检测的中文描述），帧与检测框原始数据无外发通路（02 架构「数据主权」约束）；
- **配套边界**：上传魔数 + 大小上限校验（`core/upload_guard.py`）、webhook SSRF 防护（生产仅 https + 拒内网段，`notify.allow_private_webhook` 例外可配）、密钥 `${ENV}` 环境注入不进 git、RTSP 凭据展示打码（`mask_source`）。


## Q17 智能体都能生成周报了，为什么管理端还留着周报功能？

一句话：**智能体生成的是"即时解读"，管理端交付的是"归档件"——两个入口、同一个确定性引擎，谁也不取代谁。**

- **数字同源，不会打架**：`weekly_report` 剧本的第一个动作就是调 `weekly_report_data` 工具，而该工具内部封装的正是管理端周报所用的同一个 `WeeklyReportService.gather()`（确定性 SQL 聚合，零 LLM）。两条路引用同一事实源；区别只在表达层——UI 是固定模板渲染 PDF，对话是 LLM 组织语言，且对话里每个数字强制标注来源键路径、代码回溯校验不过整体落模板（见 Q14）；
- **产物形态不同**：对话输出是即时文字解读，适合"上周安全情况怎么样"式即兴问询；管理端产出归档级交付物——固定四节结构的中文 PDF，落盘 `data/exports/`、可下载、可打印上报。生产里周报是要存档的文件，不是一段聊天记录；
- **可靠性分级**：周报是有 SLA 的周期性业务动作（督办依据、复盘留档），不能押在 LLM 可用性上。UI 路径零 LLM（结论纯规则拼接），断网照常出报；生产还有第三条路——cron 驱动 `scripts/weekly_report.py` 与 Web 进程解耦归档。三个入口各司其职：**cron 保供给、UI 保归档、智能体保便利**；
- **架构原则**：智能体不吞掉 UI——按任务特性分配入口：归档型走表单+文件，探索型走对话，周期型走 cron。给同一个确定性引擎加自然语言这扇门，而不是做两套周报。


## Q18 主题切换为什么是纯前端本地偏好，不做成后端用户配置？

- **状态归属**：主题是"这台设备/这个浏览器"的显示偏好，不是业务事实——同一账号在办公机（亮色）与大屏（暗色）的偏好本就应不同，存 localStorage 按域名隔离恰好匹配；进 users 表反而引入迁移、接口与审计噪音；
- **实现分层**：AntD token（colorPrimary/明暗算法）+ CSS 变量（`--accent-primary*`/`--fg-rgb`/表面色）双层——组件内联样式已全部变量化（白色半透明叠加统一走 `rgba(var(--fg-rgb), a)`，亮色下自动翻转为深墨叠加），因此切换零组件改动；
- **边界**：风险语义色（红/橙/绿标签）与成功色不随主题变——定级语义必须恒定。

## Q19 对话窗口的上下文与记忆是怎么做的？会不会把历史噪声带进规划？

三层，全部可关（`agent.*`）且全部落证据链：

1. **会话内摘要**（既有）：近 5 轮 digest（≤300 字代码拼接）——粗粒度沿袭；
2. **会话内原文轮次**（v2.2）：最近 2 轮 user/assistant 原文（各截 200 字）——digest 丢细节，"刚才那张单"这类指代必须靠原文理解；
3. **跨会话记忆**（v2.2）：用户最近 2 个其他会话的最新要点（digest ≤120 字），提示词里明确标注"仅供理解背景、非本轮指令"——记忆只影响理解，不影响工具参数（附件另有服务端强制绑定，LLM 编路径即拒）。

为什么不做成向量长期记忆：当前规模下"最近 K 个会话要点"确定性、可审计、零新增依赖；向量记忆库列入后续优化（09）。
